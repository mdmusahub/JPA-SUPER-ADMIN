| D-4 | S3 storage provider moves from optional v0.1 to v0.2. The storage SPI still ships in v0.1. | Reduces v0.1 scope. The SPI keeps S3 an addition, not a rewrite. |
| D-5 | Uploads are private by default (authenticated serving only). | Safer default. Matches UPL-7. |
| D-6 | The default console path stays `/admin`. | Familiar and documented. Hardening is covered by the Security page. |
| D-7 | Under the `prod` profile, startup fails if the password is under 12 characters or is a common password. Otherwise a warning is logged. | Stops weak credentials on exposed consoles without blocking local development. |
| D-8 | The console does not change global session cookie settings. It relies on Spring Boot defaults, documents that hosts should set `Secure` and `SameSite`, and logs a startup warning on plain HTTP under `prod`. SEC-8 reworded. | Session cookie settings are global and would change the host app, which breaks SEC-4. |
| D-9 | Image thumbnails are the original image scaled by CSS. No server-side resizing. | Keeps resizing out of v0.1 scope. |
| D-10 | Upload tickets: a signed token of about 10 minutes, issued with the form page, bound to entity and field, carrying max size and expiry. Validated on `POST /admin/uploads` in addition to CSRF. `jpa.admin.upload.signing-key` signs them. File serving uses session auth only in v0.1. | Limits what a stolen or replayed upload request can do. Session auth is enough for serving in v0.1. |
| D-11 | Sensitive field matching is case-insensitive, ignores `_` and `-`, and is a substring match against configured names, plus `@AdminSensitive`. | Catches `userPassword`, `api_key` and similar names that exact matching would miss. Favours masking too much over too little. |
| D-12 | Export cap is a fixed internal ceiling of 50,000 rows. `jpa.admin.export-max-rows` may lower it, never raise it. | Protects memory and the database. |
| D-13 | The HTML prototype lives at `docs/prototype/admin-console.html`. It is reference only and not shipped in the jar. | Keeps the visual reference in the repo without affecting the artifact. |
| D-14 | `DECISIONS.md` and `CHANGELOG.md` are created in Phase 0. This file is created early to record these decisions. | Decisions should be recorded when made. |
| D-15 | `PROJECT_DOCS.md` is added to the AI-1 reading list. | Consistency with `CLAUDE.md`. |

The exact version is confirmed with the maintainer before pinning. | All Spring Boot 3.x lines are out of OSS support (3.5 ended 2026-06-30). Boot 4.0 OSS support ends 2026-12-31. | D-21 | The UI and backend are built as two parallel tracks in one directory and separate module folders (`jpa-admin-ui`, `jpa-admin-ui-preview` for UI; `jpa-admin-core`, `jpa-admin-autoconfigure`, `sample-app` for backend). They meet at view-model records in `jpa-admin-core` (`io.github.mdmusahub.jpaadmin.web.view`), frozen after Phase 0. One branch per phase, no per-track branches; the phase is merged to `main` and tagged only when connected (GIT-1, GIT-2). Phases 4 and 11 are verified by MockMvc and view-model tests, with the browser check at connection. Records are public but internal (ARCH-9 exception). Records are draft until the phase that fills them starts; after that every change needs approval and a DECISIONS entry. Sensitive form fields have type `masked` and no value (SEC-1). Templates read only records (UI-12). Work stays inside your track's paths (AI-11). While both sessions are active, module builds are enough per task and the full build runs when the other session is idle (TEST-3). No inline scripts or styles; theme via blocking `theme.js`; accent colour via a validated generated stylesheet (UI-13, SEC-15, Phase 13). The `recentlyViewed` field is dropped from `DashboardView`. | Lets templates, CSS and JavaScript progress without waiting for services, with no rework at connection. Keeps the host app safe (no sensitive data in templates, a strict CSP stays possible) and avoids merge conflicts in a shared working tree. `recentlyViewed` was not in the plan or BRD. |
| D-22 | The preview is a separate, unpublished module `jpa-admin-ui-preview` (a small Spring Boot app depending on `jpa-admin-core` and `jpa-admin-ui`), not part of `sample-app` and not a profile. It has no database and no login, fails startup under the `prod` profile, and is never a dependency of the starter or `sample-app`. The build verifies this (ARCH-11). Supersedes the earlier plan to keep the preview in `sample-app` under a `ui-preview` profile. | Preview routes skip login and use fake data, so they must be impossible to publish or enable in production. A separate module makes that structural. |
| D-23 | Add the Maven Enforcer plugin with a `bannedDependencies` rule that forbids `jpa-admin-ui-preview` as a dependency of `jpa-admin-starter` and `sample-app`. | CODE-5 reason: ARCH-11 must be checked by the build, not by memory. | D-24 | Console assets live at `classpath:/jpa-admin/assets/` in `jpa-admin-ui`, served only by the console's own resource handler for `{path}/assets/**`. | D-27 | **Contract freeze (2026-11-01).** The view-model records are frozen in `jpa-admin-core/.../web/view` as plain Java 17 records with no framework dependency: `PageChrome`, `LoginView`, `DashboardView`, `ChartSeries`, `ListView`, `Cell`, `DetailView`, `FormView`, `UploadResult`, `ErrorView`, plus their nested types, exactly as in `docs/UI_PLAN.md` section 3 (without `recentlyViewed`). Rules enforced by the constructors: required values are never null, lists are copied with `List.copyOf`, a `MASKED` cell holds only `Cell.MASK` (no value, tone, href or title), a `MASKED` form field has no value, an upload field has a ticket and no other field has one. Template names are `jpa-admin/login`, `dashboard`, `list`, `detail`, `form`, `error`; model attributes are `chrome` (`PageChrome`) and `view` (the page record); the names are constants in the records. `docs/FIXTURES.md` lists the fixtures; no fixture code exists yet. Four gaps found while freezing (sort links, page links, export link, form title and id) are recorded as open questions in `docs/UI_PLAN.md` section 3, not added to the records. | The freeze lets the UI and backend tracks start from one agreed shape (D-21). Following the table exactly and listing gaps separately keeps the freeze reviewable and avoids inventing requirements (AI-4). Records stay draft until the phase that fills them starts. Making invalid states impossible (masked values, ragged rows, inconsistent empty states) in the constructors protects SEC-1 at the boundary the templates read from. |
| D-28 | **Contract follow-up: backend builds links, one link rule (2026-11-01).** The four gaps left open by D-27 are closed while the records are still draft. (1) `ListView.Column` gets `sortHref` (present exactly when sortable) and `sortState` (`NONE`, `ASCENDING`, `DESCENDING`, which must match `ListView.sort` and `dir`). (2) `ListView.Paging` gets `firstHref`, `prevHref`, `nextHref` and `lastHref` (present exactly when that page exists), and `sizes` becomes a list of `SizeOption` (size, current, href); exactly the page size in use is `current`. (3) `ListView.Actions` gets `exportHref` (present exactly when `canExport`), carrying the current search, filters, sort and visible columns. (4) `FormView` gets `title`, `entityLabel`, `recordId` (present exactly in `EDIT` mode), `actionHref` and `cancelHref`. Templates only print links. One rule applies to every link in every record, enforced in the constructors by the package-private helper `Hrefs`: a relative path that starts with a single `/`, no scheme, no `//` in the path, no backslash, no whitespace or control character; error messages name the field and never repeat the link. The rule covers `Cell.href`, `Breadcrumb.href`, `Filters.clearAllHref`, `Chip.removeHref`, the new links, and also `DetailView.Image.url`, `UploadResult.url` and `PageChrome.basePath` (templates build the fixed entity routes from it). Breadcrumbs must lie under `basePath`. `//` is rejected in the path only, not in the query, because search text such as a pasted URL is legal there; link builders must percent-encode every parameter value. A test per place a link appears checks about 30 rejected forms (schemes, `//`, backslashes, tab and line-feed tricks, spaces, relative paths) and accepted forms, and a test fails if a record gains a link component without a `Hrefs` check. `docs/UI_PLAN.md` section 3 and `docs/FIXTURES.md` are updated; the open questions are removed. | A template that has to rebuild a sort, page or export URL has to repeat the backend's query logic, and that is where search, filter and sort parameters get lost or mis-encoded. Letting the backend build links keeps the logic in one tested place. A link printed into `href`, `src` or `action` is a navigation target, so one rule that rules out `javascript:`, protocol-relative URLs and header-injection characters at the boundary stops an open redirect or script link wherever a link value later comes from; the console path rule (SEC-14) is applied to `basePath` for the same reason. `Hrefs.java` is the one non-record file in `web/view`; records in six files share the rule, and keeping it package-private keeps the public API small. |
