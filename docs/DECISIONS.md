| D-28 | **Contract follow-up: backend builds links, one link rule (2026-11-01).** The four gaps left open by D-27 are closed while the records are still draft. (1) `ListView.Column` gets `sortHref` (present exactly when sortable) and `sortState` (`NONE`, `ASCENDING`, `DESCENDING`, which must match `ListView.sort` and `dir`). (2) `ListView.Paging` gets `firstHref`, `prevHref`, `nextHref` and `lastHref` (present exactly when that page exists), and `sizes` becomes a list of `SizeOption` (size, current, href); exactly the page size in use is `current`. (3) `ListView.Actions` gets `exportHref` (present exactly when `canExport`), carrying the current search, filters, sort and visible columns. (4) `FormView` gets `title`, `entityLabel`, `recordId` (present exactly in `EDIT` mode), `actionHref` and `cancelHref`. Templates only print links. One rule applies to every link in every record, enforced in the constructors by the package-private helper `Hrefs`: a relative path that starts with a single `/`, no scheme, no `//` in the path, no backslash, no whitespace or control character; error messages name the field and never repeat the link. The rule covers `Cell.href`, `Breadcrumb.href`, `Filters.clearAllHref`, `Chip.removeHref`, the new links, and also `DetailView.Image.url`, `UploadResult.url` and `PageChrome.basePath` (templates build the fixed entity routes from it). Breadcrumbs must lie under `basePath`. `//` is rejected in the path only, not in the query, because search text such as a pasted URL is legal there; link builders must percent-encode every parameter value. A test per place a link appears checks about 30 rejected forms (schemes, `//`, backslashes, tab and line-feed tricks, spaces, relative paths) and accepted forms, and a test fails if a record gains a link component without a `Hrefs` check. `docs/UI_PLAN.md` section 3 and `docs/FIXTURES.md` are updated; the open questions are removed. | A template that has to rebuild a sort, page or export URL has to repeat the backend's query logic, and that is where search, filter and sort parameters get lost or mis-encoded. Letting the backend build links keeps the logic in one tested place. A link printed into `href`, `src` or `action` is a navigation target, so one rule that rules out `javascript:`, protocol-relative URLs and header-injection characters at the boundary stops an open redirect or script link wherever a link value later comes from; the console path rule (SEC-14) is applied to `basePath` for the same reason. `Hrefs.java` is the one non-record file in `web/view`; records in six files share the rule, and keeping it package-private keeps the public API small. |

| D-30 | **Phase 1: dependencies and design decisions (2026-11-01).** (1) Dependencies, each with its reason (CODE-5). `spring-boot-starter-webmvc`: a real dependency of `jpa-admin-starter`, so a host gets the web stack through the starter; `optional` in `jpa-admin-core` (controllers) and `jpa-admin-autoconfigure` (MVC configurers), compile-time only. `spring-boot-configuration-processor`: optional in `jpa-admin-autoconfigure`, generates the IDE metadata for `jpa.admin.*` (DOC-2). (2) Properties are validated by plain code in `JpaAdminProperties.validate()`, called from `afterPropertiesSet()`, not by Bean Validation. One startup report lists every wrong property; each message names the property and gives an example. (3) A username or password that is still a whole `${...}` placeholder after binding counts as missing. (4) Console controllers (package `io.github.mdmusahub.jpaadmin.web` and below) declare relative mappings, and a `WebMvcConfigurer` adds the base path as a prefix to those controllers only. (5) `BasePath` (core) is the one canonical console path: segments of letters, digits, `-` and `_`, each starting with a letter or digit, at most 100 characters, never rewritten, only accepted or rejected. Code builds fixed routes with `BasePath.link(...)`. (6) Types that the auto-configuration module creates from another module are public with an "internal, not stable API" Javadoc (ARCH-9 is SHOULD): `BasePath`, `PlaceholderController`, `JpaAdminAutoConfiguration`, `JpaAdminProperties`, `JpaAdminAssetsConfigurer`. (7) Replaceable beans (`@ConditionalOnMissingBean`): the placeholder controller and the assets handler. Not replaceable: base path, path prefix, password guard. (8) The password guard is `@Lazy(false)`. (9) The prod check matches the profile name `prod` exactly. (10) `sample-app/src/main/resources/application.yml` holds no credentials. Tests use fake values from `sample-app/src/test/resources/application.properties`; the demo is started with `JPA_ADMIN_USERNAME` and `JPA_ADMIN_PASSWORD` or `--jpa.admin.*` arguments. (11) The Phase 1 home page is a plain-text placeholder with no data and no login; Phase 2 puts it behind the security chain. (12) One placeholder asset, `jpa-admin/assets/css/tokens.css`, was added to the UI track's folder at the maintainer's request so the asset handler can be tested; the UI track replaces it. (3) Boot's binder leaves an unresolvable placeholder as literal text (its placeholder helper is built to ignore unresolvable placeholders), so the PLAN's own example `password: ${ADMIN_PASSWORD}` would start with that text as the password. (7) A host may want its own home page or asset serving; the others enforce rules. | D-32 | **The console's asset handler never serves hidden files (2026-11-01).** Under `{path}/assets/**`, any path segment that starts with a dot (`.gitkeep`, `.DS_Store`, `.env`, `.git/config`, `css/.hidden`) is "not found", as written or percent-decoded (`%2egitkeep`), whether or not the file exists. It is a `ResourceResolver` (`NoDotfilesResourceResolver`) at the front of the handler's chain, with no property to turn it off. The stray `.gitkeep` is also deleted from `jpa-admin-ui/src/main/resources/jpa-admin/assets/` (at the maintainer's request; this touches the UI track's folder). Tests: `DotfilesAreNeverServedTest` in `sample-app`, which puts dotfile fixtures in the real asset location next to a visible control file, and `NoDotfilesResourceResolverTest`. | Maven copies `.gitkeep` into the jar, and a handler that serves whatever is in the folder published it at `/admin/assets/.gitkeep` (reproduced: it answered 200). Deleting the file fixed that one case only; the same test with dotfile fixtures stayed red until the handler refused them. Refusing at the handler holds for any dotfile that a tool or an editor leaves in the folder, so nobody has to remember to keep them out. The answer is the same 404 whether the file exists or not, so it does not reveal what is in the jar. The resolver API is not deprecated in Spring Framework 7.0.10 (checked with `javap`). |
