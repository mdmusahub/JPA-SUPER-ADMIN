# Limitations and roadmap

Current limits: single admin account, a servlet path prefix is not supported in v0.1 (`spring.mvc.servlet.path` must be unset; otherwise the console answers 500 and logs why), password at most 72 bytes, console templates are cached and not reloaded at run time, no audit log, no login rate limiting, no inline child rows, one file per upload field, no image resizing, English only, saved views stored per browser, CSV only, servlet applications only.

Upload limits: a file sent with the plain form (no script) reloads the page and loses text typed and not saved in the record form (the page says so); the thumbnails of a list are the original files scaled by CSS; the list checks that each stored file is still there, one file test per row; replacing or removing a file keeps the old file on disk (UPL-9: files that no record holds any more pile up; a read-only report of such files exists as an internal class, `OrphanUploadReport`, with no entry point and no way to delete, and a cleanup is not part of 0.1), the host's multipart limits (Spring Boot 4.1 default: 1MB per file, 10MB per request) apply before the console's and the console never changes them, only the five types PNG, JPEG, GIF, WebP and PDF can be stored (SVG and HTML never), a plain form over the host's limit gets the server's own 413 page, an entity whose console address is `uploads` is not supported, the `public-path` is protected only by the host's own security, and Hibernate's own SQL logging at TRACE would show the stored address.

Discovery limits: an entity with a composite primary key (`@EmbeddedId` or `@IdClass`) is not supported and is left out of the console, with a one-line startup warning (entities need a single-column id in v0.1). The console reads one `EntityManagerFactory`: if the host has several and marks none `@Primary`, the console lists no entities and logs a warning rather than guessing which database it would show. Sensitive-field name matching is a case-insensitive substring match, so it can mask a field nobody meant it to (for example `tokenizer`, which contains `token`); narrow `jpa.admin.sensitive-fields` to avoid it.

List limits: a relation column shows the related record's label (the property named by `@AdminLookup`, else the first text field named `name`, `title`, `label`, `fullName` and similar, else the first text field, else `#id`) and links to that record when its entity is in the console. A relation column sorts by the related record's label. To-many relations, embedded values and binary data are not shown in the list. A text longer than 120 characters is cut, with the full text on hover. Numbers are shown as stored, dates as `yyyy-MM-dd`, and an instant in UTC. The plural in a heading is a plain English guess (`Category` is `Categories`, `Person` would wrongly be `Persons`) unless you set `@AdminResource(plural = "People")`. Each list page runs two queries, a count and a page, and the sidebar adds one count per entity at most every five seconds; on a very large table the count is not free. The page size is 25 unless `jpa.admin.page-size` says 10, 50 or 100; it is one setting for the whole console, not one per entity.

Sort and search rules:

- **What can be sorted.** A visible, non-sensitive column of kind identifier, text, number, boolean, enum, date or date-time, and a to-one relation whose target is in the console and has a label (the same label the cell shows: a text field named `name`, `title`, `label`, `fullName` and similar, else the first text field). A relation shown as `#id`, a masked column, a collection, an embedded value and binary data cannot be sorted. A sort key that is not one of these is ignored and the list is in identifier order; a valid key with a missing or unknown direction is ascending.
- **How a relation is ordered.** By the target's label, not by its identifier, through the join the list already makes: no extra query. A sensitive attribute of the target is never the label, so it can never order the list.
- **Missing values.** In every sort, records with no value in the sorted column (an empty field, or a relation that is not set) come last, in both directions, on every database. After the sorted column, rows are ordered by the identifier ascending, so paging never repeats or skips a row. Databases differ in where they put missing values by default (H2 and MySQL first, PostgreSQL last, in an ascending sort); the console does not follow them. It is tested on H2, PostgreSQL and MySQL.
- **What a search covers.** The visible, non-sensitive text fields of the entity itself (and its identifier if that is text): not numbers, dates, enums, booleans, relations, or hidden or sensitive fields. When a search finds nothing, the page lists the columns it looked in by their header names (at most ten, then "and N more"), or says that the table has no text column a search can look in. A search longer than 100 characters is cut to 100, and a notice says so and gives the limit.
- **Limits.** The order of text, including relation labels, is the database's own (upper and lower case and accents follow its collation); a relation whose target has a label that is empty or missing sorts as missing; a search that finds rows does not list its columns.

Filter rules:

- **Where.** A filter panel sits under the search box on every list page (a "Filters" button that opens it). It is part of the same form as the search, so searching keeps the filters and filtering keeps the search. The state is in the address: `filter.<field>=<value>`, so a filtered list can be bookmarked and the Back button works.
- **What can be filtered.** A visible, non-sensitive field that is not the identifier and is one of: text, number, yes/no, enum, date or date-time, or a to-one relation whose target is in the console and has a label (the same label the cell shows). A sensitive field, a hidden field, a collection, an embedded value, binary data and a relation to a hidden entity have no filter. A filter parameter that names one of them is ignored, in the same words as a name that does not exist, and no value is ever shown.
- **Parameters.** Text, enum, yes/no and relation: `filter.<field>=<value>`. Numbers: `filter.<field>.min` and `.max`. Dates: `filter.<field>.from` and `.to`, written `yyyy-MM-dd`. A blank value means "not set" and says nothing, because an HTML form sends blank controls.
- **Text.** Case-insensitive "contains". `%`, `_` and `!` are taken literally. Control characters become spaces, the ends are trimmed, and text longer than 100 characters is cut (and a notice says so).
- **Enum.** One constant name, exactly as the enum spells it. **Yes/no.** `true` or `false` in any letter case; `any` is the same as leaving it out.
- **Relation.** The dropdown lists the target's labels and sends its identifier. The identifier must be one of the choices listed, otherwise the filter is ignored. The dropdown lists at most **200** records, ordered by label (a record with no label last, shown as `#id`). **A target with more than 200 records gets no relation filter at all**, and the page says so, rather than showing a list that is silently cut short. The choices come from the target's own records and never from a hidden entity or a sensitive field.
- **Number range.** `min` and/or `max`, inclusive: digits with an optional minus sign and decimal point, no exponent and no thousands separator. A whole-number field rounds a fractional bound inwards (a minimum of 2.5 means 3 and up). A bound the field cannot hold is ignored. A minimum above the maximum ignores the whole filter.
- **Date range.** `from` and/or `to`, inclusive, real calendar days from year 1000 to 9998 (so `2026-02-30` is ignored). On a date-time field `from` starts at the first moment of that day and `to` includes the whole of that day. A date-time stored as an instant is cut into days in UTC, as its cell shows it. A `from` after the `to` ignores the whole filter.
- **Ignored values.** Never an error. The list shows without that filter, and a notice at the top names the filter by its label and says why (never repeating what was typed). A repeated parameter uses the first value and says so. A name that matches no filter is counted in one message that names nothing.
- **How many.** At most **10** filters apply at once (a range with two bounds counts as one), taken in column order; the others are ignored and counted in a notice.
- **Combining.** Filters are ANDed with each other, the search, the sort and the paging. Each active filter is a chip with a remove link, there is a "Clear all filters" link, and removing a filter or clearing all keeps the search, the sort and the page size and starts again at the first page.
- **Cost.** The count and the page use the same conditions (all bound parameters). A relation filter adds one small statement per list page for its choices (identifier and label only, 201 rows at most); a list with two filterable relation columns costs four statements, whatever the number of rows. Nothing else grows with the filters, and no join is added.
- **Not yet.** Several values for one field (v0.2), filtering on a relation's own fields, "is empty" and "is not empty" filters are not part of version 0.1. (Saved views are described under "Column visibility and saved views" on the page "Using the console".)

Record rules:

- **The detail page.** `GET {path}/{entity}/{id}`, reached from the first column of a row or from a relation. One statement; a password-like field is dots and is never read; a hidden field is absent; a collection, an embedded value and binary data show their label and "(not shown)"; a long text keeps its line breaks and, past 300 characters, sits behind a summary. The breadcrumb leads back to the list with the search, filters, sort and page the visitor came from.
- **Which ids work.** The id in the address is turned into the identifier's type: `Long`, `Integer`, `Short`, `Byte`, `BigInteger`, `UUID` or `String`. A number must be written in its plain form (`7`, not `007` or `+7`); a UUID in the usual 8-4-4-4-12 form; a text id is at most 255 characters with no control character, no `/` or `\`, and is not `.` or `..`. Any text that is not an id gives the same console 404 as an id with no record, as does a hidden or unknown entity or an entity whose identifier is a sensitive field.
- **Relation links.** A relation cell links to the related record when the related entity is in the console, and shows `#id` with no link when it is hidden or unsupported. An empty relation is an empty cell.
- **Permissions.** `@AdminResource(readOnly = true)` makes an entity show-only; `@AdminResource(creatable = false)`, `(updatable = false)` and `(deletable = false)` forbid creating, editing and deleting only. The services enforce all of them: a forged request answers 403 and never reaches the database. An entity whose identifier is a sensitive field is listed with the identifier masked but has no detail page, link, checkbox or delete.
- **Delete.** `POST {path}/{entity}/{id}/delete` with the CSRF token, after a question that needs no script. The delete runs in one transaction through the persistence provider, so the host's own mapping (cascades, `@PreRemove`) applies. A record that other records still depend on is kept and the page says so in plain words, with no SQL, table name or stack trace. A `GET` to a delete address changes nothing (405).
- **Bulk delete.** `POST {path}/{entity}/bulk-delete` with the ids in the `ids` parameter, **at most 100 per request** (the largest page; a request with more is refused and nothing is deleted). All or nothing: if one record cannot be deleted, none is. Ids that are not ids, or have no record, are skipped and counted ("Deleted 2 records. 1 selected record was skipped ..."); the same id twice counts once. The header checkbox selects the rows of the current page only, and the selection is cleared whenever a page is shown (a new page, search, filter or sort). Selecting every row that matches a filter is not part of v0.1.
- **After a delete** the visitor returns to the same search, filters, sort and page size, on the first page when something was deleted, on the same page when nothing was; a page past the end becomes the last page. The message is shown once.
- **Duplicate.** The route `{path}/{entity}/new?copyFrom={id}` checks its source (unknown, malformed and hidden sources are the console's 404; a read-only entity is 403). A copy never takes the identifier or the version, a sensitive field, a hidden field, a collection, an embedded value or binary data; a relation is copied only when its target is in the console. The route shows the create form filled with those values (see the form rules below), and the detail page offers "Duplicate record".

Form rules:

- **Where.** `GET {path}/{entity}/new` (a create form), `GET {path}/{entity}/{id}/edit` (an edit form), `GET {path}/{entity}/new?copyFrom={id}` (a create form filled from another record), `POST {path}/{entity}` (create) and `POST {path}/{entity}/{id}` (update). Every POST needs the console's CSRF token. Opening a form changes nothing. A hidden, unknown or malformed entity, id or `copyFrom` is the console's 404; an entity that may not be created in or changed is 403.
- **Which fields.** Only the visible fields of the entity's own metadata: text, number, yes/no, date, date and time, enum and a to-one relation whose target is in the console. Never the identifier of an existing record, the `@Version`, a hidden field, a collection, an embedded value or binary data; a name in the request that is none of these is never read. An identifier that the persistence layer does not generate (no `@GeneratedValue`) is an input of the create form only. A field that was not sent is empty on create and unchanged on update; an update writes only what changed.
- **Values.** Whole numbers in digits (with an optional minus sign) within the type's range; decimals with one point, no exponent or grouping; yes/no; dates as `yyyy-MM-dd` and times as `yyyy-MM-ddTHH:mm[:ss]`, real dates only (an instant or an offset time is read and shown in UTC); an enum by its constant; a relation by choosing one of the listed records. A text is stored as given (not trimmed); a text of spaces only is empty; control characters are refused; the longest text is the column's length (`@Column(length)`, 255 by default) and never more than 100,000 characters. An empty optional field is stored as no value; an empty required field is refused.
- **Errors.** A field that is wrong gets a plain sentence next to it, linked to its input, and a summary at the top links to each; nothing is saved and the form is shown again (status 422) with what was typed. The sentences say what is wrong and how to fix it; they never repeat the typed text and never name a class, a constraint or a table.
- **Sensitive fields.** A masked input that never has a value. On edit, leave it blank to keep the stored value; type a value to replace it. The console stores exactly what it is given: if the stored value should be hashed, do it in the entity's setter. Nothing typed is shown back, redirected, put in a message or written to the console's log.
- **Relations.** A select of the target's labels, at most **200** records, ordered by label. A target with more records is shown as a notice ("it keeps its current value"), and a save that would change it is refused for that field only. A required relation whose target has no record yet is a notice too.
- **Stale forms.** For an entity with a `@Version`, a save from a form that was opened before another change is refused with a plain message, nothing is saved, and the form stays stale until the record is opened again. An entity without a `@Version` has no such check (the last save wins).
- **Validation.** The console works with or without Hibernate Validator. When the host has it (for example Spring Boot's validation starter), its violations are shown next to the field they name, in the console's own words by kind of constraint (required, size, minimum, maximum, e-mail, pattern, past or future, and a general sentence for any other). Without it, the console checks what it can itself and a database refusal (NOT NULL, unique) is one sentence for the whole form. **A host note:** validation runs in the persistence layer at insert and update, so the entity's own constraints are what count.
- **After a save.** A created record returns to the list's first page; a changed one to its own page; a message says what happened (it names the record's label, never another value). The address to go to is built by the console and is never taken from the form.
- **Leaving.** "Cancel" asks "Discard your changes?" without script; with script the browser also warns when a changed form is left another way, and Cancel goes straight back when nothing changed.

More limits to know. This list adds to the limits above; none of them is removed.

- **A relation column costs one `LEFT JOIN` per relation column** (two statements per page whatever the number of columns, but each relation column adds a join to the page query). An entity with many relation columns on a large table can be slow. A column hidden with `hide` is not queried: it adds no select and no join, so a visitor who hides relation columns lowers the cost of the page; the default list still has them all. **Measured:** on the first page the joins cost nothing (20 ms with none or three on PostgreSQL); the cost shows on deep pages, about +12 ms per relation column at offset 100,000 on PostgreSQL (34 ms with none, 71 ms with three) and +20 to 30 ms on H2, because the database joins every row it skips. At this size no batch query is needed; hiding the relation columns of a view roughly halves the cost of a deep page. Beyond 200,000 rows the cost is proportional (an estimate, not measured).
- **The search is a full scan.** It is a case-insensitive "contains" (`lower(column) like '%text%'`), which an ordinary index cannot serve, so on a large table it reads the table. `count(*)` is not free either. **Measured:** a list with a search takes 150 to 620 ms on PostgreSQL and 80 to 430 ms on H2 (the count scans every row, and a deep page scans further); `count(*)` of the whole table is 10 to 15 ms on PostgreSQL; sorting by a column with no index sorts the whole table (75 to 210 ms). **Index advice, PostgreSQL:** one `pg_trgm` GIN index per searched column (`create index ... using gin (lower(column) gin_trgm_ops)`; the console ORs every visible text column, so every one needs its own) made a rare search about 10 times faster (174 ms to 16 ms); it does not help a word that is in every row. MySQL has no equivalent for `like '%text%'`, so a MySQL host keeps the scan. Index the sort columns you use.
- **Database portability.** The same 69 list, search, sort, filter, export, detail, create, edit, stale-form, delete and chart scenarios, and a start of the whole demo application, run on H2, PostgreSQL 17.11 and MySQL 8.4.11 (see "Database support" below). **One limit holds on all three: an entity with a `@Lob String` attribute cannot be searched** (Hibernate refuses `lower(...)` on a large object before the database is asked, so the list service fails and the console answers with its error page, as said it would; the failure of the service is tested on all three databases, the error page itself was not exercised over HTTP in this phase); the list without a search works, and its cells are cut. This is a known issue that is not fixed in 0.1: until it is, keep such an attribute out of the entities you need to search, or map the text without `@Lob`.
- **The phone-width behaviour is proven in a real browser on every build**: headless Chrome or Edge, through a driver written with the JDK only, checks every page type at 1280 and 390 pixels in both themes. The checks are skipped, with the reason, where the build machine has no Chrome or Edge. What no automated browser judges (a screen reader, a physical keyboard and phone, dragging a file onto the drop zone, print, a real private window) is checked by hand before a release.
- **Null ordering is one rule, proven on H2, PostgreSQL and MySQL**. Records with no value in the sorted column come last in both directions. Hibernate writes the clause only where the database's default differs, so the SQL differs by database and the result does not.
- **A search says what it covers only when it finds nothing**. A search that finds rows does not list its columns.
- **A relation's label is not searched**, although it can be sorted. Finding records by a relation's label is the relation filter: choose the record from the dropdown. A relation shown as `#id` cannot be sorted. The order of labels is the database's text order (case and accents follow its collation); PostgreSQL and MySQL ignore case, H2 does not (see "Database support").
- **Filters are limited to what is listed under "Filter rules" above**: one value per field (multi-value filters are v0.2), the identifier cannot be filtered, a text filter is a "contains" like the search (a full scan on a large table, see the search limit above), and a relation filter costs one small extra statement per filterable relation on every list page.
- **A relation cell is a link only when its target is in the console**. A relation to a hidden or unsupported entity shows `#id` with no link.
- **The export follows the list and nothing else**: the file is the list's search, filters and sort, its visible non-sensitive columns (a column hidden with `hide` is left out), up to 50,000 rows; a negative number arrives as text because of the formula guard; a relation arrives as its label (or its plain id); a file cut at the cap is said so in two headers and in a notice on the list page; rows are read with an offset, so the last pages of a very large file cost more than the first; a record added while a large file is written can shift a row between pages. Excel and LibreOffice were not opened in the automated tests (a manual check).
- **The page size is one setting for the whole console** (`jpa.admin.page-size`: 10, 25, 50 or 100, default 25); a page size per entity is not offered. The plural, the badge tones and the relation label are choices of the host with `@AdminResource(plural)`, `@AdminBadge` and `@AdminLookup`; the badge palette is four tones (`green`, `amber`, `red`, `grey`), with no blue and no free colour.
- **Accessibility statement.** Measured in a real browser on every build, in the light and the dark theme, on the dashboard, the list, detail, create, edit and not-found pages (with every panel open): the colour of every visible text, placeholder and chart label against what is drawn behind it is **at least 5.16 to 1** (WCAG 2.2 needs 4.5 for normal text and 3 for large text); the keyboard focus ring is 5.70 to 1 (light) and 9.83 to 1 (dark) against the page; every link, button, form control, summary, image and table has an accessible name; there is one `main` landmark and one top-level heading per page; ids are unique; the page language is declared; two skip links lead past the sidebar; the drawer keeps keyboard focus inside itself; every stop of the Tab order on the list, detail, create and edit pages shows a focus ring and is on screen; motion is reduced when the system asks for it. **Known limits:** the border of a text field is 1.52 to 1 (light) and 1.67 to 1 (dark) against the panel (below the 3 to 1 that WCAG 1.4.11 asks of a control's boundary; each field has a visible label, so it is identifiable without the border, and darkening it would change the whole look); the measurements used the default accent colour `#0d9f6e`; every other shade derives from `--ac` with `color-mix`, so a very light or very dark `jpa.admin.primary-color` can fail contrast and should be checked (for example by running `ContrastBrowserTest` with your colour); hover colours, print, a screen reader's speech and reading order, and a physical keyboard and phone have not been judged by a person (a manual check before each release).
- **Browser tests cannot cover** a screen reader, drag and drop of a file, the native file dialog or the native "leave this page?" dialog (only the event that asks for it is checked), a real private window, hover and focus colours beyond the ring, print and the look of a design.
- **Detail and delete limits.** An identifier of a type other than the seven listed (a `char`, a date, a floating-point number) gives no detail page and no delete. A `String` identifier that holds a `/` (or is `.` or `..`) cannot be written into an address, so its row has no link and the record cannot be opened or deleted in the console; an identifier with an encoded slash, a NUL byte or `..` in an address is refused by Spring Security's HTTP firewall with a plain 400, before the console is asked. A composite identifier is still unsupported.
- **A delete reads the whole row.** The console deletes through the persistence provider so that the host's mapping applies, and Hibernate loads the record it removes. The console itself never logs a value (its log line holds the entity's address and the kind of failure), but with Hibernate's `org.hibernate.orm.jdbc.extract` logger at TRACE a sensitive column of the record being deleted is in Hibernate's own log. Do not enable that logger in production.
- **The cap of 100 records per bulk delete is not configurable** in v0.1, and one failing record rolls back the whole batch (by design). The messages say how many were deleted; they do not say which record blocked the batch.
- **The bulk bar and the header checkbox need script;** without script the row checkboxes, the question and the submit button still work, and the header checkbox is not shown.
- **Form limits.** An identifier type other than the seven of the detail page, a field of a type with no input (a `Calendar`, a `LocalTime`, a collection, an embedded value, binary data) and a relation to a hidden entity are not part of the form, so a record that needs one of them cannot be created in the console. A relation with more than 200 records cannot be set (a typed-id box is not offered in v0.1). There are no read-only fields, labels or help texts of the host's choosing (`@AdminField` is planned for a later version).
- **Typed values reach Hibernate's log if the host asks for it.** With `org.hibernate.orm.jdbc.bind` at TRACE every bound value of an insert or update, a typed password included, is in Hibernate's log; the console's own log lines never hold a value. Leave that logger off in production.
- **The stale check needs a `@Version`.** An entity without one has no such check: the last save wins.
- **A date and time is shown to the millisecond** (the most the input holds). An edit that does not touch it leaves the stored value as it is; one that does writes the millisecond value.
- **Saved views and hidden columns.** Views live in the browser's `localStorage`: clearing site data removes them, they are not synced, and the 20 views per entity, the 60-character name and the dropped-quietly rules are the ones listed under "Column visibility and saved views". The Columns panel has a "Show all columns" link (there exactly when a column is hidden). "Clear search" and "Clear search and filters" keep the hidden columns.
- **A detail page for a very wide entity** prints every visible field; there is no field selection on the detail page; hiding columns applies to the list and its export.

### Database support

| Database | Version tested | Driver | How it runs |
|---|---|---|---|
| H2 | 2.4.240, in memory (the demo's own database) | H2 2.4.240 | every test of the project |
| PostgreSQL | 17.11 (official image `postgres:17.11`, Debian 17.11-1.pgdg13+2) | PostgreSQL JDBC 42.7.14 | a container started by Testcontainers 2.0.5, once per test class |
| MySQL | 8.4.11 (official image `mysql:8.4.11`, the long-term-support line) | MySQL Connector/J 9.7.0 | the same |

Hibernate ORM 7.4.13.Final finds the dialect from the connection on all three. Other databases and versions (MariaDB, SQL Server, Oracle, older or newer PostgreSQL and MySQL) were **not** tested; to try another version of the two containers, pass `-Djpa.admin.test.postgres-image=postgres:<tag>` or `-Djpa.admin.test.mysql-image=mysql:<tag>`.

**What runs on each database.** In `jpa-admin-core`: 69 shared scenarios (paging, the last page clamp, a host default page size of 50, search with `%`, `_`, `!` and backslash taken literally, an injection attempt, non-ASCII text, text columns of 4,000 and 20,000 characters, sorting every column both ways with the identifier as tie-breaker and nulls last, every filter kind, hidden relation columns dropping their joins, export in pages of 500 and cut at the cap, the detail page, create, edit, the stale form (also the one raced past the check), a unique-constraint refusal with no SQL in it, delete, delete of a record in use, an all-or-nothing bulk delete, a write after a refused write, the chart per zone and at its cap, numbers and moments of every Java type, a UUID identifier). In `sample-app`: the whole demo application started on each database over real HTTP, with 6 checks (the dashboard and its chart, every entity's list searched and sorted by every field both ways, the CSV of every entity, a record opened, created, refused when it clashes, edited and deleted, a category in use kept, the next request after a refusal). Run them with `mvn -B -pl jpa-admin-core test -Dtest='H2EngineTest,PostgreSqlEngineTest,MySqlEngineTest'` and `mvn -B -pl sample-app -am test -Dtest='*SampleEngineTest' -Dsurefire.failIfNoSpecifiedTests=false`. They need Docker; **without Docker on a laptop every container test is skipped with the reason (never passed), and on CI (`JPA_ADMIN_REQUIRE_ENGINES=true`) a missing Docker fails the build.**

**Known differences between the databases** (each one is asserted by a test that names the engine; none changes what the console shows, except where said):

| Difference | H2 | PostgreSQL 17.11 | MySQL 8.4.11 |
|---|---|---|---|
| Order of text (a sort, the label order of a relation) | by code point: `C:\temp` before `a_b` | follows the collation (`en_US.UTF-8` in the official image): ignores case, `a_b` before `C:\temp` | follows the collation (`utf8mb4_0900_ai_ci`): ignores case (and, by the collation's name, accents) |
| A moment stored with an offset (`OffsetDateTime`, `ZonedDateTime`) | comes back with the offset it was stored with | comes back as the same instant in UTC | comes back as the same instant in UTC |
| What the page shows for such a moment | the wall clock of the stored offset (`05:06`) | the UTC wall clock (`23:36`, the day before in this example) | the UTC wall clock |
| Sort by a `@Lob String` attribute | by the text | by the large object's number (the creation order), because Hibernate stores it as an `oid` | by the text |
| Search on an entity with a `@Lob String` attribute | fails | fails | fails (a Hibernate 7 check, before the database is asked) |
| A date and time kept with nanoseconds | to the microsecond | to the microsecond | to the microsecond (the page shows the minute, the form the millisecond) |
| After a refused statement (a unique or foreign key violation) | the next request works (tested) | the database aborts the transaction; the console rolls back and the next request works (tested) | the next request works (tested) |

The same on all three, and tested: records with no value come last in both directions; the identifier breaks ties so pages never repeat or skip a row; `lower(...) like ... escape '!'` finds ASCII and non-ASCII text in any case (on PostgreSQL this relies on a UTF-8 database, as in the official image; a `C` locale database was not tested); `%`, `_`, `!` and `\` in a search are literal; a `BigDecimal` keeps its value; `long`, `short`, `double`, `float` and `BigInteger` round-trip exactly; a unique-constraint or foreign-key refusal reaches the visitor as one plain sentence with no SQL, table or constraint name.

**An environment trap, not a console defect.** The PostgreSQL driver sends the JVM's time zone name as the session's time zone, and the official PostgreSQL image (Debian 13) no longer knows the legacy alias that some JVMs report for a zone (`Asia/Calcutta`): the connection is refused with `invalid value for parameter "TimeZone"`. A host whose JVM reports such a name should start with `-Duser.timezone=Asia/Kolkata` (the canonical name). The tests of `jpa-admin-core` pin `Asia/Kolkata` once, before the first test class (`PinnedTestZone`), so they give the same result on a laptop in India and on a runner in UTC. It has to be once: H2 reads the JVM's default zone the first time it converts a date and keeps it, so a test that changes the default zone afterwards makes a stored `LocalDate` come back a day early. A host that changes the JVM's default zone while the application runs can see the same thing in an H2 database; set the zone at start-up (`-Duser.timezone`).

**Measured limits** (200,000 rows, a laptop, H2 and PostgreSQL in Docker; the measurements are repeatable with `mvn -B -pl jpa-admin-core -Pperf test`): first page 3 ms (H2) and 20 to 28 ms (PostgreSQL), middle page about 70 ms on both, last page 120 to 140 ms; a page with three relation columns is invisible at the start and adds about 12 ms per column at offset 100,000 on PostgreSQL; a search costs 80 to 620 ms and a trigram index makes a rare one about 10 times faster on PostgreSQL; sorting by an unindexed column 75 to 210 ms; the export of 50,000 rows about 2.2 s; the chart read at its cap 31 to 37 ms on PostgreSQL. These are not guarantees: a server is faster than this laptop, a network between the application and the database is slower.

Chart limits: the chart reads up to 50,000 timestamps per chart entity every 5 seconds at most, whatever the range, so index the creation column of a very large table; counts are incomplete beyond 50,000 records in 90 days (the card says so); `java.util.Date` and `java.sql.Timestamp` creation fields are not recognised; days follow the server's time zone (or the host's `Clock`), not the viewer's; the chart query runs on H2, PostgreSQL and MySQL and costs 31 to 37 ms per entity at the cap on PostgreSQL (22 to 80 ms on H2), so no database function is needed; the one-transaction-per-entity isolation of a broken table is proven on H2 only; the browser pass of the card (both themes, phone width, keyboard, script off) is a manual item.
