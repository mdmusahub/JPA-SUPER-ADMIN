- `ListQueryService` has one shared `project(...)` (list and export), `Plan.checked` (the second check of every name, SEC-2) and `exportPlan`/`exportRows`. Hiding is one more filter on the plan's columns, so the list and the export cannot disagree.

## Design

### The `hide` parameter (decision 3)

`hide=<column key>`, **repeated** (`?hide=price&hide=created`), not comma separated. Reasons: it reads like `filter.*`, each name is checked on its own (an unknown name is ignored without touching the others), a comma can legally be in no attribute name so nothing is gained by joining, and "show everything" is the plain address. A comma-joined value is one name that is not a column, so it is ignored.

Accepted names: the key of a **visible, non-sensitive** column of the entity (`ListColumns` minus the `MASKED` ones). A hidden (`@AdminHidden`) attribute is not a column at all, a sensitive field is a masked column that can never be hidden (it keeps showing dots, as D-58 says the column exists). The identifier can be hidden. Everything else (unknown, empty, over 100 characters, a repeat) is ignored one by one, silently, so a sensitive name cannot be told from an unknown one (D-62 point 5 style). At most 200 `hide` values are read.

**At least one column stays (decision 4).** If the accepted names cover **every** hideable column, the whole `hide` is ignored and the page shows a plain WARNING notice: "Every column was hidden, so all columns are shown. A list needs at least one column." (it repeats nothing the visitor typed). The rule is applied twice, in the parser and in `Plan.checked` (as the sort key is), so a `ListQuery` built by hand cannot hide the last column. A masked column never counts as the visible one.

### Core (`jpa-admin-core`)

| Piece | What |
|---|---|
| `service/HiddenColumns` (new, package-private rules, public result record `HiddenParse`) | `parse(entity, registry, rawValues)` returns `hidden` (accepted keys in column order, distinct) and `everyColumnHidden`; `check(plan columns, hidden)` is the same rule for `Plan.checked` |
| `ListQuery` | seventh component `hidden` (`List<String>`, column order, distinct, at most 100). The 5- and 6-argument constructors stay. `withHidden(list)` and `withoutHidden()` start again at page 0, like every change of what the list holds; `withParsedHidden` keeps the page (the address that carries the hide also carries the page); `withSort`, `withSize`, `withPage`, `withFilters` carry `hidden` |
| `ListQueryService` | `parseHidden(entity, values)`; `Plan.checked` re-validates `hidden`; `project(root, plan, selectId, hidden)`: a hidden column is **not selected and not joined**; the only exception is a hidden relation column that is the sort key, which keeps its join **for the `ORDER BY` only** (the scope's recommendation: sort and search are conditions of the query, not display); `rows` gives a hidden column `Cell.empty()`; `exportPlan` drops the hidden columns from `ExportPlan.columns()` and `exportRows` does not select them |
| `ListLinks` | `link(...)` writes `hide=<encoded key>` for each hidden column after the filters and before `sort`; `export(...)` carries them too (the Phase 11 Javadoc promised it); no other link changes |
| `ListViewFactory` | `Column.visible = !hidden`; the row link: the identifier cell, or when the identifier is hidden the row's first visible non-empty text or number cell (so a row is always a way to the record); the notice text `hiddenColumnsNotice()` |
| `EntityController`, `ExportController` | read `hide` (`request.getParameterValues`), `parseHidden`, `withParsedHidden`; the list adds the every-hidden notice |

No change to any `web.view` record, annotation, property or dependency. `jpa-admin-core` stays free of Spring Boot, Security and Thymeleaf.

### Query cost (decision 5)

`project(...)` skips a hidden column entirely: no selection, and for a relation no `LEFT JOIN`. The recorded SQL of a page with hidden relation columns has fewer joins and a shorter select list (tests count `left join` occurrences and name the attributes with `RecordingStatementInspector`). The count query never had joins. The relation **filter choices** (one small statement per filterable relation, D-63) are not display, so hiding a column does not remove them. The search still looks in a hidden text column (it is a condition, not display); the empty-state hint names the columns the search looks in, which can include a hidden one, and that is documented.

### UI (`jpa-admin-ui`)

| Piece | What |
|---|---|
| `fragments/column-panel.html` (new) | a `details` panel "Columns" inside the toolbar GET form, next to Filters: one checkbox per non-masked column, `name="hide"`, `value` the key, **checked = hidden**, each with a visible label; the summary shows how many are hidden; a button "Apply columns"; works without script (a submit reloads the list without `page`). A masked column has no checkbox and its key is printed nowhere |
| `fragments/views-panel.html` (new) | a `details` panel "Views" **outside** the toolbar form (no form inside a form): an empty state "No saved views yet", a save form (a labelled name field, "Save current view"), a `<template>` for one view row (link, "Rename" details with a field and a button, "Delete" details with the question and the confirm button, each with an `aria-label`), a status line (`aria-live`). Everything that needs storage is script-only; without script the panel says plainly that saved views need script and browser storage and the Columns and Filters panels still work |
| `list.html` | includes the two panels; the views panel carries the data the script needs: `data-views-base` (`basePath/entity`), `data-views-state` (the **effective state link** of this page, that is the href of the current page-size option: `q`, filters, `hide`, `sort`, `dir`, `size`, never `page`), `data-views-columns` (keys of the non-masked columns), `data-views-filters` (keys of the filter definitions) |
| `layout.html` | `views.js` with `defer` |
| `assets/js/views.js` (new) | the only file that touches `localStorage` for views. Key `jpa-admin.views.<basePath>.<entity>`. Reads and writes only inside `try/catch`; stores only the view JSON (`name, q, filters, sort, dir, pageSize, hiddenColumns`); never `document.cookie`, never `fetch`, `XMLHttpRequest`, `sendBeacon`, `WebSocket` or a form post, never `innerHTML`, never reads a token, ticket, password or CSRF value. A view is cleaned before it is used or stored (`name` 1 to 60 characters, no control character; `q` at most 100; at most 10 filters, names matching the page's filter keys, values at most 100 characters; `sort` a known column; `dir` `asc` or `desc`; `pageSize` one of 10, 25, 50, 100; `hiddenColumns` known, distinct and not all of them); a stored view that does not parse or fails any check is **dropped quietly** and the cleaned list is written back. At most 20 views; saving under an existing name replaces it (case-insensitive); a 21st is refused with a plain status message; a rename to another view's name is refused. A view link is `base + "?" + parameters` with every value encoded by the same rule as `ListLinks.encode` (`encodeURIComponent` plus `! ~ * ' ( )`), never a `page`, built only from the cleaned view; the script checks the base against the link rule (single leading `/`, no `//`, no backslash or whitespace) before it prints any link. All text goes in with `textContent` and links with `setAttribute('href')`, never `innerHTML` |
| CSS (`components.css`/`pages.css`) | panel layout beside the filter panel, a column checklist grid that wraps, view rows, the status line, both themes through the existing tokens, phone width, visible focus, reduced motion (nothing animated) |

### Mutation checks (Step 7), one at a time, MD5 before and after

(a) accept a sensitive column in `hide`; (b) let hiding remove the last visible column; (c) export a hidden column; (d) accept an unknown name in a saved view (`views.js` cleaning); (e) allow a 21st saved view; (f) let `views.js` write a cookie or send a request; (g) store a sensitive value in a view (the template hands a masked column's key to the script); (h) drop the reset to page 1 on a view change; (i) an unencoded view link (Java link writer, and the script's encoder).
